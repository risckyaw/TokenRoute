=== Feature 1: Expression-based pricing (port of new-api pkg/billingexpr) ===
TokenRoute prices are flat {prompt_per_1m, completion_per_1m} per model (internal/usage, config `prices:`). new-api defines pricing as one expression string per model, evaluated with expr-lang/expr:
  `p <= 200000 ? tier("standard", p*1.5 + c*7.5) : tier("long_context", p*3.0 + c*11.25)`
Variables: p (prompt tokens, billable), c (completion tokens), len (total input length for tier conditions), cr (cached-read tokens), cc (cache-creation tokens), img, ai. Coefficients are real USD per 1M tokens. Expression result = total USD cost. A `tier(name, expr)` call records the matched tier name.
Implement:
- internal/pricing/expr.go: compile+cache expressions (expr-lang/expr, bounded cache ~256 entries), env {p,c,len,cr,cc,cc1h,img,ai,ao float64}, function tier(name string, cost float64) float64 that records name.
- Token normalization (port of new-api BuildTieredTokenParams): when the expression references cr/cc/img/ai (detect via AST introspection of used vars), subtract those from p (completion-side vars from c); clamp at 0. Anthropic-semantic usage (input_tokens is text-only) does NOT subtract; instead len = p + cr + cc. Detect anthropic semantics by provider type, which the pricing call site knows.
- Config: `prices:` entries gain optional `expr: "..."` (string). When present it wins over flat fields entirely for chat cost. Flat fields remain for everything else.
- Usage extraction: the server already parses upstream `usage` — extend it to capture prompt_tokens_details.cached_tokens, cache_creation_tokens (and anthropic cache_creation_input_tokens / cache_read_input_tokens), image/audio detail tokens when present. Feed them into the expr env.
- Usage log: record the matched tier name in the log entry (new column `price_tier TEXT`, nullable; add to the existing ALTER-migration list in internal/usage).
- X-TokenRoute-Cost-USD header continues to work (expr result).
- Tests: claude-style tiered boundary (200000 exact), cache-read subtraction, anthropic no-subtraction semantics, flat-price fallback when no expr, invalid expr rejected at config load (fail fast at startup), tier name recorded.
Feature 2 (cached-token pricing) is a SUBSET of this — an operator writes `p*2 + c*8 - cr*1.8` or uses cr explicitly; no separate cache_ratio field needed. Document that in README instead of implementing a second mechanism.

=== Feature 3: Configurable retry/disable policy (port of new-api status_code_ranges + AutomaticDisableKeywords) ===
TokenRoute hardcodes retryable statuses (429/500/502/503/504) and failure classification in internal/router/failure.go. new-api makes them config: retry ranges (default {100-199, 300-399, 401-407, 409-499, 500-503, 505-523, 525-599}, never 504/524) and disable: status ranges (default 401) PLUS case-insensitive keyword match on the error body (default keywords like "insufficient balance", "account suspended" — check new-api defaults and pick a sane small set).
Implement:
- Config: top-level `retry_policy: {retry_status_ranges: "100-199,300-399,401-407,409-499,500-503,505-599", never_retry: [504,524], disable_status_ranges: "401", disable_keywords: [...]}`. All optional; unset = current hardcoded behavior EXACTLY.
- Parser for ranges (shared, tested). Wire into the failover decision (server.go) and failure classification so a keyword hit classifies like auth/quota (opens circuit fast) — map keyword matches to FailureQuotaExhausted when the keyword looks billing-related (contains "balance"/"credit"/"quota"/"insufficient"), else FailureAuth.
- Keyword matching: plain strings.ToLower + strings.Contains per keyword is fine at this scale (<= 20 keywords). Case-insensitive.
- Tests: range parse, retry matrix vs defaults, never_retry wins, keyword classification, config-load validation errors.

=== Feature 5: Weighted token estimator (port of new-api service/token_estimator.go) ===
TokenRoute estimates prompt tokens as len(messages JSON)/4 (server.go estimateChatTokens). new-api uses a weighted heuristic calibrated per provider family: count chars by class (word, number, CJK, symbol, math symbol, URL delimiter, @, emoji, newline, space) × per-family weights. Weights (from new-api):
  openai: word 1.02, number 1.55, cjk 0.85, symbol 0.4, math 2.68, urldelim 1.0, atsign 2.0, emoji 2.12, newline 0.5, space 0.42
  gemini: word 1.15, number 2.8, cjk 0.68, symbol 0.38, math 1.05, urldelim 1.2, atsign 2.5, emoji 1.08, newline 1.15, space 0.2
  claude: word 1.13, number 1.63, cjk 1.21, symbol 0.4, math 4.52, urldelim 1.26, atsign 2.82, emoji 2.6, newline 0.89, space 0.39
  (units: tokens per char-class-unit; words counted as runs, numbers as runs, CJK per char; result is sum — see new-api token_estimator.go for exact segmentation; approximating faithfully is fine, document deviations)
Implement internal/server (or internal/router) estimator: estimateWeighted(text, family). Use it in estimateChatTokens: extract text content of messages (string content + text blocks), sum weighted estimate per message, + small fixed per-message overhead (4). Family comes from the provider TYPE of the first candidate (openai/anthropic/gemini → openai/claude/gemini weights). Feed the better estimate everywhere len/4 was used: context-window guard, budget pre-check. Keep it fast (single pass over runes).
Tests: english prose sanity (~words*1.3±50%), CJK text much higher than len/4 (CJK chars ~0.85-1.21 tok/char vs 0.25), empty, family selection.

=== Feature 6: Group ratio (port of new-api group_ratio) ===
TokenRoute keys and candidates already have `groups`; routes have `multiplier`. Add per-key-group price multiplier: config top-level `group_ratio: {vip: 1.0, free: 1.2}` mapping group name → multiplier. Effective cost multiplier = route.multiplier × product of ratios of the intersection groups (key groups ∩ candidate groups; if intersection empty → 1.0). Apply at cost computation (usage log cost_usd and X-TokenRoute-Cost-USD), NOT at routing/filtering. Unset group_ratio = current behavior. Document semantics: a key in groups ["vip"] hitting a candidate in ["vip","us"] gets ratio of "vip". Multiple matching groups: multiply all (documented; usually one).
Tests: single group, multi-group product, no intersection = 1.0, unset = unchanged.

=== Feature 7: Affinity key from request header + skip_retry_on_failure (extend previous session's affinity) ===
Previous session implemented prompt-prefix affinity (internal/router/affinity.go, config `prompt_cache_affinity`). new-api generalizes the affinity key source: header (e.g. session/thread id used by Codex CLI), and supports SkipRetryOnFailure (a pinned request that fails must NOT retry elsewhere because state lives on that channel).
Implement:
- Config per route: `affinity: {enabled: true, key_header: "X-Session-Id", ttl_ms: 3600000, skip_retry_on_failure: false}` — key_header set = pin by that header's value (hash it); when unset, falls back to prompt-prefix hashing (existing behavior). Route-level `prompt_cache_affinity: true` remains as shorthand for {enabled: true} with prefix hashing. Global `prompt_cache_affinity` default unchanged.
- skip_retry_on_failure: when the request was served via a pin (affinity hit) and the upstream call fails with a retryable error, do NOT fail over to other candidates — relay the failure to the client. Rationale comment in code (stateful channel). Only applies when pin actually HIT (not when merely recorded).
- Decision header: existing `;affinity=hit` stays; add `;affinity=key:header` vs `;affinity=key:prefix` marker (keep it short: `;aff=h` / `;aff=k` — document).
- Tests: header-key pin roundtrip, distinct header values isolate pins, skip_retry blocks failover on hit, failover proceeds normally when no pin.
