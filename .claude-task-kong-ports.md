=== Feature 1: Upstream rate-limit headers feed the QuotaLedger ===
Providers (OpenAI, DeepSeek, Anthropic) return real quota state in response headers: x-ratelimit-remaining-requests, x-ratelimit-remaining-tokens, x-ratelimit-reset-requests, x-ratelimit-reset-tokens (values like "123", "45s", "2m30s" — OpenAI duration format). Kong's response-ratelimiting plugin feeds limiters from upstream headers instead of local guesses; TokenRoute's QuotaLedger (internal/router/quota.go) currently only tracks locally-observed usage against configured quota_token_limit.
Implement:
- After EVERY upstream response (success or 429), parse those four headers (case-insensitive; also accept anthropic-style anthropic-ratelimit-* prefixed variants if trivially covered by the same parser).
- New method on QuotaLedger: ObserveUpstream(provider, model string, remainingTokens int64, resetIn time.Duration) — stores an external observation {remaining, resetAt, observedAt}. When present and fresher than 60s, quota-aware strategies (reset_aware, fill_first, auto, and the new least headroom logic) use the OBSERVED remaining/reset instead of the local ledger computation for that provider+model.
- Wire into server.go response handling for chat + embeddings (non-stream: after response; stream: after headers received is fine — read from resp.Header before relaying).
- resetIn parsing: accept integer seconds and OpenAI duration strings ("1s", "1m30s", "6h"). Invalid/missing headers = no observation, zero cost.
- Tests: header parse matrix, observation freshness window, strategy preference of observed over local, absent headers no-op.

=== Feature 2: Peak EWMA + time decay + slow-start (Kong balancer/latency.lua, Finagle PeakEwma) ===
TokenRoute's least_latency uses a fixed-alpha EMA with no time decay and "unseen first" (new providers get ALL traffic instantly — a thundering-herd problem when a circuit closes or a provider is added).
Implement in internal/router:
- Replace the latency EMA state with {ewma, lastTouched}. On read/write apply lazy decay: w = exp(-dt/10s); ewma = ewma*w + rtt*(1-w). DECAY_TIME = 10s (Kong default).
- Slow-start seeding: a provider with no EWMA data is seeded with the MEAN ewma of providers that have data (Kong calculate_slow_start_ewma) instead of 0/unseen-first. If NO provider has data, treat all as equal (fall back to priority order). Apply to least_latency, p2c, auto, and fusion's candidate pick.
- New strategy `peak_ewma` (register in ValidStrategy + README table): pick 2 candidates at random, choose the lower decayed-ewma/weight score (Kong PICK_SET_SIZE=2, score = ewma/weight, candidate weight from route config default 1).
- Update least_latency to order by decayed ewma (same numbers, now decayed).
- Tests: decay math (10s half-life behavior), slow-start seed = mean, seed absent when all unseen, peak_ewma picks lower score, weight division.

=== Feature 3: least_connections strategy (Kong balancer/least_connections.lua) ===
TokenRoute `headroom` counts requests in the last 60s (historical rate); it cannot see long-running in-flight SSE streams. Kong tracks live connections in a binary heap scored (count+1)/weight.
Implement:
- Router per-provider in-flight counter: IncInflight(provider) on candidate acquire (when the upstream request is actually sent), DecInflight(provider) when the response body is fully relayed/closed OR the request fails. Cover both stream and non-stream paths (defer-style hook in server.go chatCompletions/embeddings/fusion).
- New strategy `least_connections`: order candidates by (inflight+1)/weight ascending; ties → priority. Unseen (0 inflight) naturally first via +1 scoring only when equal counts differ by weight (follow Kong semantics exactly).
- Expose inflight in the auto composite score as an additional normalized signal (weight it modestly, e.g. 15%, renormalize existing weights — keep it simple and documented).
- Prometheus: tokenroute_inflight{provider} gauge.
- Tests: inc/dec pairing on success, stream abort, failure; strategy ordering with weights; gauge value.

=== Feature 4: consistent_hash strategy (Kong balancer/consistent_hashing.lua) ===
TokenRoute affinity pins are TTL-cache based (lost on restart). Kong's consistent hashing maps a request value to a candidate deterministically with zero state.
Implement:
- New strategy `consistent_hash` with route-level config `hash_on: "header:X-Session-Id"` (any header name) or `hash_on: "key"` (the virtual API key). Missing value → fall back to priority order.
- Ring: candidates sorted by (provider,model) lexically; index = fnv32(value) % len(candidates); walk the ring forward skipping candidates filtered out by circuit-open/quota-exhausted/tag mismatch (they're simply skipped during the walk, next in ring).
- This is stateless: no TTL, no map. Affinity (F5/F7 from earlier sessions) still wins when a pin exists — consistent_hash is the strategy, pins pre-empt strategies as they do today.
- Tests: determinism (same header → same candidate), ring walk skips open-circuit candidate, different values spread, missing header → priority fallback, lexical sort stability.
- README strategy table entry.

=== Feature 5: Synthesized Retry-After on key rate-limit 429s ===
TokenRoute surfaces Retry-After for daily_quota and upstream-429 relay, but a 429 from the key's own RPM/TPM bucket lacks Retry-After (clients can't back off intelligently). Kong writes Retry-After on its own 429s.
Implement: when rejecting with 429 due to key RPM/TPM token-bucket exhaustion, compute seconds until the bucket refills enough for one request (tokens_needed / refill_rate, or window reset if that's the model used) and set Retry-After + RateLimit-Reset accordingly. Keep existing daily_quota behavior.
Tests: RPM exhaustion 429 carries sane Retry-After (>0, <=60); TPM case; daily path unchanged.
